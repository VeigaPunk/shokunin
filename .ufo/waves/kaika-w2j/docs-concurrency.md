# Jujutsu under many concurrent agents — documentation scout

**Scope.** This is a source review for the installed `jj` 0.45.1 named in the assignment context, not a concurrency reproduction or a live-repository probe. Primary claims below use the matching versioned jj documentation; later behavior is called out separately. No jj command was run.

## Verdict

**Unsafe for many independent agents sharing one jj repository on 0.45.1 without a strict external workflow guard.** jj’s operation log is deliberately concurrent, but a workspace is not an isolation boundary: operations, bookmarks, and history are repository-wide. In this version, `jj undo` has no cross-workspace guard, and `jj op restore` restores repository state rather than one agent’s workspace. Keep agents in separate repositories if they need independent history/recovery, or quiesce the shared repo before history rewrites and global restore/undo. This is a source-based risk assessment, not proof that every local concurrent run fails.

**No jj config makes undo/op-restore workspace-local in 0.45.1.** The operating rule is external. Upgrading to 0.46.0 adds a default cross-workspace refusal for `undo`/`redo`, but does not turn the operation log or `op restore` into workspace-local state; see [0.46.0 changelog](https://docs.jj-vcs.dev/latest/changelog/#0460-2026-10-07).

## Observed behavior in jj documentation

### Operation concurrency: lock-free does not mean serialized

- Each command loads a consistent view at the latest operation. A command already running does not see changes another process writes after that load; it writes its own operation with its original starting operation as parent. Two concurrent commands may therefore produce sibling operation heads rather than block or revalidate against each other. jj stores operations/views content-addressably and publishes operation-head filenames atomically. [Concurrency — “Operation log”, “Merging divergent operations”, “Storage”](https://docs.jj-vcs.dev/v0.45.1/technical/concurrency/#operation-log)
- When a later command finds multiple operation heads, jj three-way merges the views using a common ancestor. Non-conflicting view changes can merge; conflicting bookmark moves are retained as conflicted targets (e.g. a bookmark moved to either target), not silently chosen. The repository remains usable, but commands requiring an unambiguous conflicted bookmark can fail. [Concurrency — “Merging divergent operations”](https://docs.jj-vcs.dev/v0.45.1/technical/concurrency/#merging-divergent-operations)
- An operation view records shared repository facts, including bookmarks, tags, Git refs, visible heads, and the working-copy commit **for each workspace**. `jj op log` is the shared operation history, not a per-workspace journal. [Operation log — “Introduction”](https://docs.jj-vcs.dev/v0.45.1/operation-log/#introduction)

**Interpretation:** the op-head protocol is designed to preserve and reconcile concurrent repository transactions, not to provide agent-level isolation or guarantee that the commands’ semantic intent commutes. Expected outcomes include conflicts, sibling operations, and stale workspace materializations.

### Operation divergence is not divergent change

- **Divergent operations** are concurrent branches in the operation-log DAG; jj later merges the views as above. [Operation log — “Divergent operations”](https://docs.jj-vcs.dev/v0.45.1/operation-log/#divergent-operations)
- **Divergent changes** are multiple visible commits with the same change ID. They can arise when different processes/workspaces amend the same logical change, or when an IDE/background operation races an edit. A change can be divergent even when operation heads have been reconciled. [Handling divergent changes — “What are divergent changes?”](https://docs.jj-vcs.dev/v0.45.1/guides/divergence/#what-are-divergent-changes)
- jj 0.45 adds experimental `jj converge`, which uses heuristics and may prompt; the docs explicitly say no algorithm can always infer the user’s intended result. Alternatives are abandon one side, assign a new change ID to retain both, squash together, or leave divergence unresolved. [Handling divergent changes — “How do I resolve divergent changes?”](https://docs.jj-vcs.dev/v0.45.1/guides/divergence/#how-do-i-resolve-divergent-changes); [0.45.0 changelog](https://docs.jj-vcs.dev/v0.45.1/changelog/#0450-2026-09-02)

### `jj workspace add` versus Git worktrees

- In **0.45.1**, `jj workspace add DEST` creates another jj working copy with a `.jj/` directory linked to the main repo. Each workspace can check out a different commit; absent explicit `-r`, the new working-copy commit is based on the current workspace’s parent(s). This shares one repository and its operation log; it is not a cloned repo per agent. [Working copy — “Workspaces”](https://docs.jj-vcs.dev/v0.45.1/working-copy/#workspaces); [CLI reference — `jj workspace add`](https://docs.jj-vcs.dev/v0.45.1/cli-reference/#jj-workspace-add)
- The 0.45.1 Git compatibility matrix says **`git-worktree: No`**, while noting jj’s own multiple-working-copy mechanism. So `jj workspace add` in this version is not a drop-in creator of Git worktrees for tools that require the normal Git worktree metadata. [Git compatibility — “Supported features”](https://docs.jj-vcs.dev/v0.45.1/git-compatibility/#supported-features)
- Starting in **0.46.0**, `jj workspace add --colocate` / `--no-colocate` can control whether an associated Git worktree is created; Git 2.42.0 or newer is required. This adds Git-worktree compatibility, not independent jj operation histories. [0.46.0 changelog](https://docs.jj-vcs.dev/latest/changelog/#0460-2026-10-07)
- A workspace becomes stale if, for example, another workspace rewrites its working-copy commit or an interrupted command fails to update the files. `jj workspace update-stale` updates it, and if the prior operation was lost can create a recovery commit from the working-copy contents. [Working copy — “Stale working copy”](https://docs.jj-vcs.dev/v0.45.1/working-copy/#stale-working-copy)
- Colocation allows Git and jj commands to be mixed, but docs recommend mostly read-only Git commands: interleaving mutating Git operations raises the chance of confusing bookmark conflicts or divergent change IDs; jj ignores the Git staging area and does not support Git hooks. [Git compatibility — “Colocated Jujutsu/Git workspaces” and “Supported features”](https://docs.jj-vcs.dev/v0.45.1/git-compatibility/#colocated-jujutsugit-workspaces)

### `jj undo` and `jj op restore` scope

- In 0.45.1, `jj undo` means undo the last operation by restoring its parent; repeating it continues farther back. The versioned CLI documents no cross-workspace option. Because all workspaces contribute to the single op log, “last operation” can be an agent’s snapshot/operation from a different workspace. [CLI reference — `jj undo`](https://docs.jj-vcs.dev/v0.45.1/cli-reference/#jj-undo); [Operation log — “Introduction”](https://docs.jj-vcs.dev/v0.45.1/operation-log/#introduction)
- `jj op restore <operation>` creates a new operation restoring repository state to that earlier view (effectively undoing all later operations); it does not erase the intervening operation log. `--what` is marked experimental and defaults to `repo` plus `remote-tracking`: `repo` means jj repo state and local bookmarks; `remote-tracking` means remote-tracking bookmarks. There is no documented workspace-only selector. Since the restored view contains each workspace’s recorded working-copy commit, treat this as repository-wide, not a rollback scoped to the caller’s workspace. [CLI reference — `jj operation restore`](https://docs.jj-vcs.dev/v0.45.1/cli-reference/#jj-operation-restore); [Operation log — “Introduction”](https://docs.jj-vcs.dev/v0.45.1/operation-log/#introduction)
- `jj op revert <operation>` is different: it applies an inverse of one selected operation rather than restoring the whole repository to an old point. It is still a repository operation, not an agent-local undo. [CLI reference — `jj operation revert`](https://docs.jj-vcs.dev/v0.45.1/cli-reference/#jj-operation-revert)
- Cross-workspace undo guard is a **later** feature: 0.46.0 refuses `jj undo`/`jj redo` of an operation from another workspace by default, with `--allow-cross-workspace` to override. That guard is not in 0.45.1. [Changelog — “0.46.0”](https://docs.jj-vcs.dev/latest/changelog/#0460-2026-10-07); [0.45.1 CLI reference — `jj undo`](https://docs.jj-vcs.dev/v0.45.1/cli-reference/#jj-undo)

## Issue evidence and version boundaries

- **Open report matching multi-workspace agents:** [jj issue 8737](https://github.com/jj-vcs/jj/issues/8737) reports simultaneous workspace work hitting a “sibling of the working copy’s operation” internal error; after `jj workspace update-stale`, the reporter had many divergent commits that were hard to reconcile. The report specifies jj 0.35.0, so it is evidence of a failure mode, **not** proof it reproduces on 0.45.1.
- **Direct undo/agents example:** [jj issue 10181](https://github.com/jj-vcs/jj/issues/10181) describes a human undoing back past a mistaken rebase while other workspaces’ agents had created snapshots; those snapshots were undone and agents then saw stale-workspace errors and apparent missing edits. The reporter says the work was recovered from the op log. The issue was fixed by 0.46.0’s cross-workspace undo refusal, confirming the specific safeguard is absent from the installed 0.45.1 line.
- **Stale-update recovery UX:** [jj issue 7229](https://github.com/jj-vcs/jj/issues/7229) records an older report of `update-stale` apparently deleting edits. Later, the reporter clarified the work had not actually been deleted; it was far down the operation log and recovered there. Treat this as a recovery/diagnostic hazard, not proof of permanent data loss.
- **Concurrent workspace creation:** [jj issue 9314](https://github.com/jj-vcs/jj/issues/9314) documented concurrent `jj workspace add` leaving the caller unusable, but it was closed as fixed in 0.41.0; do not count it as an unpatched 0.45.1 defect.
- **Storage boundary:** jj’s concurrency documentation warns the Git backend is not wholly lock-free for repositories synchronized over NFS/Dropbox/rsync; corruption of the change-ID index is possible there, with `jj debug reindex` documented as recovery. [Concurrency — “Syncing with rsync, NFS, Dropbox, etc”](https://docs.jj-vcs.dev/v0.45.1/technical/concurrency/#syncing-with-rsync-nfs-dropbox-etc); [issue 2193](https://github.com/jj-vcs/jj/issues/2193). This warning is specifically about distributed/shared-filesystem synchronization; it is not evidence that ordinary same-disk local agent concurrency corrupts the index.

## Practical conclusion / remaining unknowns

For this fleet’s high-parallelism use, do not equate “lock-free operations” or “one workspace per agent” with independent undo or conflict-free changes. Keep shared-repo agents from running global undo/restore or rewriting other workspaces’ working-copy commits; prefer distinct repositories when independent recovery is required. If adopting jj 0.46+, `workspace add --colocate` better fits Git-worktree-based tooling and `undo` gets a cross-workspace guard, but `op restore` remains broad and concurrent rewrites can still stale other workspaces or create divergent changes.

Unresolved from documentation alone: whether the older open stale-workspace report is fixed in 0.45.1; how `op restore` updates every secondary workspace’s on-disk files in a concurrent run; and the actual failure rate under this fleet’s workloads. No scratch-clone concurrency probe was assigned or run, so these are not represented as tested behavior.
