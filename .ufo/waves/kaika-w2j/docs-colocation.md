## What `jj git init --colocate` changes

For a normal existing Git checkout, `jj git init --colocate` creates Jujutsu workspace/repository metadata (`.jj`) beside the existing `.git` and uses that existing Git repository as its backing store; it does not make a second clone. The init code selects the existing `.git` as an external Git backend, initializes the `.jj` workspace, imports existing branch/tag refs, then snapshots the current working copy. See [`cli/src/commands/git/init.rs`, init mode and setup](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/commands/git/init.rs#L100-L255), [`lib/src/workspace.rs`, `init_external_git`/`init_with_backend`](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/workspace.rs#L225-L365), and [Git compatibility: creating/colocated workspaces](https://docs.jj-vcs.dev/v0.45.1/git-compatibility/#creating-a-repo-backed-by-an-existing-git-repo).

Colocation is the v0.45.1 default (`git.colocate` defaults on); the flag explicitly enables it if configuration disabled the default. `--no-colocate` does the opposite. For an existing repository, initialization imports refs first; that init-specific importer is explicitly documented in source as not moving Git `HEAD`. The subsequent normal colocated snapshot/import lifecycle handles the current worktree's Git `HEAD`. [Init flags and config selection](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/commands/git/init.rs#L47-L82) [and init importer](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/commands/git/init.rs#L278-L312).

## HEAD and refs: two distinct synchronization paths

- **Git `HEAD` is per-worktree state, not the selected jj branch.** In colocated operation, the active workspace imports its own Git `HEAD`; if Git changed it, jj imports that commit and resets the working-copy state to it, assuming Git already updated the files. The normal jj transaction path sets Git `HEAD` to the first parent of jj's working-copy commit. When that parent changes, jj writes `HEAD` as a direct object ID (detached), not as a symbolic branch. This is why the docs say jj commands *usually* leave Git detached and advise `git switch <branch>` before mutating Git workflows that require an attached branch. This is conditional on HEAD/working-copy parent changes, not a claim every read-only command always detaches. [Docs, colocated-workspace behavior](https://docs.jj-vcs.dev/v0.45.1/git-compatibility/#colocated-jujutsugit-workspaces); [`cli/src/cli_util.rs`, snapshot/import of HEAD](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/cli_util.rs#L1328-L1448) and transaction reset/export ([same source](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/cli_util.rs#L2344-L2410)); [`lib/src/git.rs`, `import_head` and `reset_head`](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/git.rs#L1174-L1213) and [HEAD writer](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/git.rs#L1782-L1882).
- **Branches/tags are refs imported/exported independently of `HEAD`.** Source maps `refs/heads/<name>` to a local bookmark (`<name>`; represented on the Git side as remote `git`), `refs/remotes/<remote>/<name>` to remote bookmarks, and `refs/tags/<name>` to tags. Import scans Git local branches, remote branches, and tags, imports commits reachable from changed refs, and merges tracked refs into jj bookmarks/tags. A local Git branch is tracked by default. jj bookmark/tag changes export back as Git branch/tag refs; export detects when both Git and jj moved the same ref and does not blindly overwrite that conflict. In colocated workspaces the normal jj lifecycle automatically imports/exports; Git-side ref changes appear in `jj op log` as `import git refs` and can be undone/restored with jj operation commands. [Docs, colocated workspaces and caveats](https://docs.jj-vcs.dev/v0.45.1/git-compatibility/#colocated-jujutsugit-workspaces); [`lib/src/git.rs`, ref mapping/import](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/git.rs#L332-L365), [import/ref enumeration](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/git.rs#L590-L730) and [export](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/git.rs#L1326-L1415); [`cli/src/cli_util.rs`, per-command snapshot and ref import](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/cli_util.rs#L1328-L1357) and [transaction export](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/cli_util.rs#L2344-L2405).
- **A Git-made commit in the active colocated checkout:** if Git `HEAD` advances, jj imports the new HEAD commit on its next normal snapshot/import, resets the jj working-copy state to that commit, and separately imports any moved branch ref. The files are not rewritten by the HEAD-import step because Git already changed them. If the Git commit is detached, the new commit is visible via that active worktree's `HEAD`, but does not thereby acquire a named branch.
- **A Git-made commit or branch move in another Git linked worktree:** local branch refs live in the shared Git repository; jj's ref importer enumerates `refs/heads` and so will import a branch ref moved by a sibling worktree on a subsequent colocated jj command. **Inference from source:** a commit reachable only from a sibling worktree's detached `HEAD` is not found by this ref scan; `import_head()` is passed only the active jj workspace root, while sibling `HEAD`s are not branch refs. It becomes discoverable through this path if a shared branch/tag is moved to it. The source's exporter does enumerate Git worktrees: if jj is about to move/delete a branch currently checked out in any Git worktree, it detaches that worktree's HEAD at its existing commit before exporting the ref update. [`lib/src/git.rs`, branch/ref enumeration](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/git.rs#L895-L1005), [active-worktree HEAD import](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/git.rs#L1174-L1213), and [export's linked-worktree HEAD handling](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/lib/src/git.rs#L1326-L1415).

## `git worktree` boundary in 0.45.x

The docs explicitly mark **`git-worktree: No`**; use jj's own `jj workspace` commands for multiple jj working copies. In source, `jj git init --colocate` refuses to initialize inside a linked Git worktree (where Git's per-worktree `git_dir` differs from `common_dir`) and advises initializing at the main Git repository or using `jj workspace add`. The v0.45.0 changelog says per-worktree Git `HEAD` state was added as preparation for future multi-Git-worktree colocation, not as support for it. Thus, shared branch refs from sibling Git worktrees can be imported as above, but a raw `git worktree` is not a supported additional colocated jj workspace in this version. [Docs, supported features](https://docs.jj-vcs.dev/v0.45.1/git-compatibility/#supported-features); [`cli/src/commands/git/init.rs`, linked-worktree rejection](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/commands/git/init.rs#L206-L219) and [detection](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/cli/src/commands/git/init.rs#L403-L412); [v0.45.0 changelog](https://github.com/jj-vcs/jj/blob/7c41cdeb16b6b321c64e789a966b6adf723816a5/CHANGELOG.md#L68-L71).

## Other documented unsupported / partial Git behavior

The v0.45.1 compatibility list marks `.gitattributes`, Git hooks, submodules in the working copy, partial clones, Git LFS, and Git's `worktree` feature unsupported. Shallow clones are only partial: deepening/unshallowing is not supported. Git staging/index semantics are ignored; jj does not understand Git's representation of merge conflicts, unfinished Git rebases, or some less common Git repository states. Annotated-tag creation is unsupported (jj can read annotated or lightweight tags and creates lightweight tags). Git configuration support is partial (the docs call out remote configuration and `core.excludesFile`). jj has native replacements for multiple workspaces and sparse checkout (`jj workspace`, `jj sparse`). Colocation also increases interleaving-related branch/divergence conflicts and import cost with very many refs; the docs flag NFS/Dropbox concurrency as less resilient and not thoroughly tested. [Official v0.45.1 compatibility list and colocated caveats](https://docs.jj-vcs.dev/v0.45.1/git-compatibility/#supported-features) and [colocated-workspace caveats](https://docs.jj-vcs.dev/v0.45.1/git-compatibility/#colocated-jujutsugit-workspaces).

## Assessment boundary

High confidence for documented 0.45.1 semantics; the only inference above is the sibling detached-HEAD visibility limit, derived from the active-root `import_head()` and ref-only enumeration. This is a source/docs assessment, not a live-repository probe or per-repository safety verdict.
