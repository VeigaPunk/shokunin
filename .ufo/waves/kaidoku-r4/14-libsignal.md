# kaidoku-r4 · 14-libsignal — Rust-native `.node` addons: static recovery of a stripped neon registration surface

Axes: **fringe-depth** (how far a stripped 25 MB Rust `.node` yields to stock tools + REA), **registration-recovery** (can the JS-visible export table be reconstructed without symbols), **provenance-fidelity** (crate/version/SBOM extraction from panic strings), **wall-honesty** (where the pipeline actually breaks and whether the break is configurable). Primary target `@signalapp+libsignal-client.node` (24,944,200 B); `libringrtc-x64.node` (14,540,960 B) as the second family-B specimen.

## Candidate: The napi-rs-family taxonomy holds; the binding layer is specifically **neon 1.1.1**

- claim: All 4 `.node` under `/usr/lib/signal-desktop` are stripped `ELF 64-bit LSB shared object, x86-64, DYN`. libsignal-client = 24,944,200 B, sha256 `1b44ed531f404f5358ee0618a423560463819534a38db5176bb1064b9d14d1f7`, BuildID `9a6b70b0bf20314635f1924a5e149469295169bc`; libringrtc-x64 = 14,540,960 B, sha256 `2e6294594009c4900ac67258fde5c40e6543aba788df22b4a5bb90e31cc3ea23`; sqlcipher = 2,183,600 B; xattr = 35,112 B. Both Rust modules confirm the r3 family-B rule: **zero ` U napi` undefined imports** (libsignal: 143 total imports, of which 3 are `dlopen`/`dlsym`/`dladdr`; ringrtc likewise), each exporting exactly `T napi_register_module_v1` (libsignal @ vaddr `0x1533c50`, ringrtc @ `0xd56250`). The specific binding layer is **neon**: `.rodata` carries `neon::types::Deferred`, `neon::event::Channel::send`, `neon::types::JsBox`, `neon::handle::Root`, `neon threadsafe function` panic strings and a `neon-1.1.1` crate-src path — not raw napi-rs. Roughly 20+ `napi_*` names survive as length-prefixed strings (the dlsym() lookup keys); NEEDED libs are only `libstdc++/libgcc_s/libm/libc/ld-linux` for libsignal, plus `libpulse/libdl/libpthread` for ringrtc.
- source: `find /usr/lib/signal-desktop -name '*.node'` + `file`/`sha256sum`/`nm -D`/`readelf -d`/`strings` on all four; `strings | grep neon` and `grep -oE 'napi_[a-z_]+'` on both Rust modules

## Candidate: The whole JS export surface is recoverable stripped — 741 descriptors, `{name_ptr, name_len, shim_fn_ptr}` in a linkme distributed slice

- claim: libsignal exports **741 `D signal_register_node_<Name>` data symbols** (the single largest dynsym block, 741 of ~765 defined dyn syms). They are not callable exports: each is a 24-byte record in the `linkme_LIBSIGNAL_FNS` section (`.data`, vaddr `0x17c7ca0`, size `0x4578` = 17,784 B = 741 × 24). Layout proven three ways: (a) file bytes at each record are `{0, len, 0}` — pointer fields arrive via **1,482 `R_X86_64_RELATIVE` relocs** (exactly 2 × 741); (b) record 0 of `Aes256GcmSiv_New` @ `0x17cb198`: reloc addend `0x2525e0` → `.rodata` bytes `Aes256GcmSiv_New`, len field `0x10` = 16 = strlen, addend `0xd84d00` → `.text` shim that compares arg buffer len `0x20` (the AES-256 key size) inline; (c) slicing every name_ptr by its len field reproduces **all 741 dynsym names byte-exactly (741/741, 0 mismatches)** — names are packed Rust `&str`s, NOT NUL-terminated C strings. Name census: **560 production exports + 181 `TESTING_*` exports shipped in the release build** across 146 namespaces — top: UnauthenticatedChatConnection 26, AuthenticatedChatConnection 22, ServerPublicParams 13, ServerSecretParams 12, SenderCertificate 12, PreKeyBundle 12, GroupSecretParams 11, RegistrationService 10, plus zkgroup/Svr2/HsmEnclave/backup/crypto/registration surfaces and one `registerErrors` + `MinidumpToJSONString` diagnostic.
- source: `nm -D | grep ' D signal_register_node_'` (741); `readelf -S -W` (linkme_LIBSIGNAL_FNS geometry); `readelf -rW` reloc scan; python length-sliced string resolution
- verify: `nm -D <f> | grep -c ' D signal_register_node_'` → 741; `readelf -SW <f> | grep linkme_LIBSIGNAL` → `0004578` B; `readelf -rW <f> | awk 'in range' | wc -l` → 1482
- verified-at: 2026-10-13 13:52 -03
- suggested: admit — this inverts the usual "stripped = surface lost" assumption: neon's linkme registration keeps the complete JS API table as *exported data*, so `nm -D` alone recovers every export name, and one reloc pass recovers each name's shim address. The 181 `TESTING_*` exports (deterministic-RNG toggle, panic/borrow harnesses, BackupListMediaTests, ConvertOptionalUuid…) are a release-build hygiene finding worth flagging: test scaffolding is reachable from JS in the shipped artifact.

## Candidate: The linkme/`linkm2` section pair is the registration engine; `napi_register_module_v1` is a slice-walking trampoline

- claim: dynsym exposes six boundary pairs: `__start/__stop_linkme_{MAIN,LIBSIGNAL_FNS,EXPORTS}` in `.data` (FNS span 0x17c7ca0–0x17cc218, EXPORTS *empty* — both bounds at 0x17cc218) and `__start/__stop_linkm2_{MAIN,LIBSIGNAL_FNS,EXPORTS}` in `.rodata` (8 B each — one fn-ptr element apiece). `napi_register_module_v1` (objdump at its real vaddr `0x1533c50`, ~0x230 B) is a pure trampoline: TLS-guard once-init (`__tls_get_addr`, set `[rax+0x168+8]=1`), loads three 56-byte statics (the linkme `DistributedSlice` objects: `{__start,__stop}` fat pointers) via GOT-indirect `.data.rel.ro` slots, then loops `call QWORD PTR [rbp+r13]` over an 8-byte-stride fn-ptr slice; each called initializer yields descriptor batches consumed by a per-export registrar at `0x1538e60`, early-exiting on return discriminant `al==2`. No `napi_*` symbol appears in the disasm — the napi calls are `call QWORD PTR [rip+X]` through `.data.rel.ro` slots populated by dlsym at init, which is exactly how a zero-`U napi` module still calls N-API. ringrtc's `napi_register_module_v1` (`0xd56250`) is the **identical codegen template** — same 0x58-frame prologue, same TLS gate, same 56-B static loads, same `[rbp+r13]` call loop — proving the trampoline is a neon-emitted constant across builds (rustc 1.99-nightly vs 1.97.1 produce the same shape).
- source: `nm -D` boundary symbols both files; `objdump -d -M intel --start-address=0x1533c50 --stop-address=0x1533e80` and `0xd56250+0x1b0`; `readelf -SW` linkme section geometry
- verify: `nm -D <f> | grep -c '__start_linkm'` → 12 (libsignal); `objdump -d -M intel --start-address=0x1533c50 <f> | grep 'call.*\[rbp+r13'` → the slice walk
- verified-at: 2026-10-13 13:55 -03
- suggested: admit — gives the third fingerprint for family B: `__start/__stop_linkm{e,2}_*` exported boundary syms + empty `linkme_EXPORTS` + a sub-600-byte trampoline. The trampoline byte-shape is stable enough to recognize neon registration in any future stripped artifact without running it.

## Summary
signal-desktop's two big `.node` addons are neon-1.1.1 Rust modules of the r3 family-B species — zero ` U napi` imports, N-API bound lazily by `dlopen/dlsym` into `.data.rel.ro` thunks, both exporting the same sub-600-byte TLS-gated trampoline `napi_register_module_v1` that walks `linkme`/`linkm2` distributed slices. The headline recovery result: **stripping does not hide the JS surface** — libsignal's entire export table survives as 741 `D`-type `signal_register_node_*` descriptors `{name_ptr,name_len,shim_fn_ptr}` (560 production + 181 `TESTING_*` names resolved byte-exact via reloc addends), while ringrtc's ~40 `ringrtc::electron::*` export names persist in panic strings, so both APIs enumerate with `nm -D`/`strings` alone, no decompiler needed. Panic-location `.rs` paths double as a versioned SBOM (163 crates incl. neon-1.1.1/tokio-1.52.3/curve25519-dalek-5.0.0) and module map (`libsignal_net`, `libsignal_protocol`, `zkgroup`, `spqr` post-quantum ratchet); `.comment` pins rustc 1.99-nightly vs 1.97.1 and `.gnu_debuglink` names the shipped `.debug` companion. REA side: ringrtc `analyze` landed clean — `ev_9e89880c…`, ghidra 12.1.4, 36 segments / 28,122 procedures / 12,276 strings in 304 s. libsignal `analyze` hit the wall at three measured points — 330 s (stock), 1,142 s, and 2,402 s with `REA_GHIDRA_STARTUP_TIMEOUT_MS` overrides provably honored (`timeout_ms` echoes each value) — always dying inside Ghidra's decompiler passes (112K+ `DecompileCallback`s) under r4 fleet CPU contention, never reaching `list_documents` readiness. Two operational corrections recorded for later lanes: `--snapshot` stores a binding manifest, not a program cache — every CLI verb re-pays the full Ghidra import+analysis (a `search` on ringrtc spawned a fresh project and exceeded 300 s); and `kill_shell` does not reap the `npx→node→java` tree — orphan Ghidra jobs keep burning cores after their wrapper dies.
