## 2. Method

- **Phase A (acceptance)** — one minimal request per candidate effort value in the M1 D6 shape (`input` list, `store:false`, `stream:true`, no `temperature`, `max_output_tokens` 16, prompt `"ping"`) plus the effort field: `reasoning: {"effort": <value>}`. Values: `high`, `xhigh`, `max`, `ultra`, plus an `invalid-control` (`r18-invalid-effort`) that separates "the backend validates this field" from "the backend ignores it" (M2 methodology). Each record keeps the exact request bytes + sha256, HTTP status, error body, the response's own `reasoning` echo and the usage block.
- **Phase B (measurement)** — for every accepted value at or above the current high pin, n=2 sequential reps of the M3 battery's fixed performance prompt at `max_output_tokens` 256, TTFT/TPS derived exactly as the battery derives them (battery/scripts/protocols.py): TTFT is content-only, the decode span starts at the first delta of any kind, TPS is `(completion_tokens − 1) / decode span` with `completion_tokens` from the server's usage block, and a span under 50 ms is recorded as burst, not throughput. A same-window `omit` control (no `reasoning` key, byte-shape identical to the M3 battery body) runs first, because the M3 baseline itself was measured without an effort field on the wire: `battery/scripts/protocols.py` `build_body(..., codex=True)` adds only `store:false`, no `reasoning` key.
- **Quota politeness** — one attempt per value in phase A, n=2 in phase B, 16/256-token outputs, sequential requests, no retries; a 401/403/429 wall would have stopped the run (none occurred). 13 requests, 2067 output tokens.
- **Redaction** — request headers persist names with the credential value replaced by a length marker; response headers keep values only for an allow-list (tracing ids, `x-codex-*` quota telemetry; the per-turn state blob is length-marked).

## 7. Decision — the variant to register

Per the mission rule: if `ultra` is not an accepted wire value, state that plainly and register `max` (or `xhigh` if `max` were rejected). `ultra` is not accepted; `max` is. The variant is therefore an **`max` pin**, named for the value it actually sends on the wire — a `-ultra` name would claim a value the backend validates and rejects. Splice-ready text: `SPLICE-QUOTE.md`.

- **Alias** `openai-codex/gpt-6.1-sol-max`; **provider** `openai-codex`; **model** `gpt-6.1-sol` (same upstream id as ranks 1–2); **`overrides.default_effort = "max"`**; `support_efforts` kept to the sibling list `[low, medium, high, xhigh, max]` — every value in it is on the wire's accepted list, and `ultra` is deliberately absent because it is rejected (it was never declared-and-working; this mission is the wire evidence).
- **Why the pin is real (documented asymmetry, quoted in SPLICE-QUOTE.md):** for pool-bound subagents the variant's `default_effort` wins over the global `[thinking].effort`, and only `[secondary_model].default_effort` outranks it. That is the recipe from the config-files documentation, *Different thinking efforts per pool entry*; the variant copies all metadata fields in full per that recipe (the docs' stated prerequisite: `default_effort` must be a member of `support_efforts`, and a variant inherits nothing).
- **Honest scope caveat:** with the live global `[thinking] effort = "max"`, a pool-bound subagent on the plain `openai-codex/gpt-6.1-sol` entry resolves to the global value too (the same `max` on the wire today); the variant's distinct value is that it holds `max` explicitly and independently of the global setting, and that it names the operator's intent. It is not an independently measured provider path: same shim, same upstream model id as ranks 1–2 (M3 SELECTION s3 logic applies).
- **Verify-after-apply:** every number here measures the backend at an explicit `reasoning.effort` value over direct HTTP with the lane's own headers. The variant has *not* been measured as a pool entry — application and a dispatch through the pool are the operator's step, and the effort resolution on the subagent path (documented asymmetry above) is the one behaviour this probe cannot exercise. Confirm it on the first dispatch: the shim's request log or a capture should show `reasoning.effort: "max"` for the subagent's turns.
- **M5 fast-mode stands orthogonal.** M5's `service_tier` finding (*accepted but never confirmed applied; timing delta within noise; NO-GO on a routing entry*, M5 s1) concerns a different field and a different axis — priority servicing is a speed tier, `reasoning.effort` is reasoning depth. Neither probe exercised the other's field; this mission changes nothing about M5's no-go, and M5's conditional-go protocol for fast mode is untouched.

## 8. Limitations

- n=2 per value, one window, one machine, one shim (2026-10-15 14:28:58Z→14:29:57Z). The M3 baseline was measured in an earlier window without an effort field; the same-window `omit` control is the drift check, not a third rep.
- Acceptance used a 16-token budget; the measurement uses the M3 perf prompt at the M3 cap, so every rep's content is a capped prefix, as in M3/M5.
- Correctness probes were not re-run for the new variant (M8 scope is the effort tier and its TTFT/TPS). The 9/9 correctness figures in the routing table belong to the sibling entries of the same upstream model; do not copy them onto the new line as if M8 had measured them.
- `low` and `medium` were not re-probed by M8 (out of the 'at or above the high pin' scope; they are in the validator's accepted list and already declared by the live sibling entries).
- The `ultra` catalog entry is model-agnostic evidence; only `gpt-6.1-sol` was probed. A different model on this fleet could accept `ultra`; this lane's shim serves `gpt-6.1-sol` and `gpt-6-luna` (SHIM_MODELS).
